# ola0-00: cómo se mergea un PR de la Ola 0 (común a todas las specs ola0-*)

Phase / wave: Ola 0 (integración)
Model: Sonnet · Effort: Medium
Can run in parallel with: no es una tarea; es el procedimiento que siguen las demás.

## Goal
Que quien mergea (el Lead de la fase; `docs/WORKFLOW.md`) siga siempre el mismo procedimiento seguro de CLAUDE.md («Mergeo autónomo»), sin mirar conversaciones antiguas.

## Reglas
- **De uno en uno.** La regla de `main` exige rama al día (`strict_required_status_checks_policy`): tras cada merge, el siguiente PR se pone al día con `main` y vuelve a pasar el CI completo (~25 min). Se pueden *preparar* varios PRs en paralelo, pero se mergean en serie.
- **Poner al día:** `gh api -X PUT repos/dsvmotion/moodly/pulls/<n>/update-branch -f expected_head_sha=<head>` (commit de merge; nunca rebase ni force push). Si hay conflicto (422), lo resuelve el autor o un worker con `git merge origin/main` en la rama, nunca reescribiendo historia.
- **Revisión:** tras poner al día, el agente `reviewer` (`.claude/agents/reviewer.md`) comprueba que el commit de merge solo trae `main` (el diff propio del PR es idéntico al del head revisado). Si el PR cambió de verdad, revisión completa.
- **Sacar de borrador:** `gh api -X POST repos/dsvmotion/moodly/pulls/<n>/ccr/ready_for_review` (en sesiones en la nube GraphQL está bloqueado; usar estas rutas REST).
- **Comprobaciones antes del merge (todas):**
  1. Los 5 checks de `scripts/merge-guard/required-checks.txt` con su ejecución más reciente sobre el head exacto en `success`.
  2. El status `sensitive-paths` más reciente publicado por `github-actions[bot]` en `success`.
  3. `check-sensitive.sh` **de `origin/main`** (nunca el del PR) sobre la lista de archivos y el diff del PR (`gh api -H "Accept: application/vnd.github.v3.diff" repos/dsvmotion/moodly/pulls/<n>`); si toca `packages/evals/baseline.json`, con sus dos versiones (`scripts/merge-guard/baseline-versions.sh`). Salida 0.
  4. Comentario en el PR con resumen, evidencia y archivos (con el pie `Generated by Claude Code`).
  5. Merge: `gh api -X PUT repos/dsvmotion/moodly/pulls/<n>/merge -f merge_method=squash -f sha=<head comprobado>`. Nunca sin `sha`.
  Hay un script REST que hace 1–5 en `docs/reports/2026-11-24-cierre-v1.md` (anexo A).
- **Después del merge:** comprobar que el CI de `main` sobre el commit del merge termina en verde (corre lo mismo que el anexo B; no se repite en local) y vigilar «Despliegue a staging» y `/health` del worker. Si algo falla: arreglar o revertir y avisar a Diego.
- **Aserciones cambiadas:** si un PR cambia aserciones existentes, explicarlo a Diego **antes** del merge (no se mergea sin su visto bueno).
- **Migraciones:** el timestamp tiene que ser posterior a la última de `main` (si no, `db push` no la aplica en staging). Número de pgTAP sin repetir.
- **Flake conocido:** el e2e a veces muere en «Supabase local (mínimo)» con `address already in use` en 54322, antes de ningún test. Un único relanzamiento: `gh api -X POST repos/dsvmotion/moodly/actions/runs/<run>/rerun-failed-jobs`. Si GitHub cancela el e2e por concurrencia («higher priority waiting request»), cancelar la corrida vieja del mismo PR y relanzar la cancelada.
