## 1. El producto y el objetivo
- Plataforma B2B de agentes de IA que hacen trabajo real dentro de pymes, medianas y cadenas con varios locales.
- Cada empresa tiene 4 agentes (`reception`, `customer`, `sales`, `admin`) que conocen el negocio, aprenden (memoria cruzada entre agentes y locales), trabajan contra objetivos y hacen de coach.
- Objetivo del lanzamiento (piloto, M3): un negocio real de belleza o servicios atiende a sus clientes por WhatsApp y chat web con Recepción y Atención al cliente: huecos, reservas, cambios, recordatorios, lista de espera, respuestas desde su conocimiento y paso a una persona.
- El equipo del negocio aprueba desde la app lo que no es autónomo; sus calendarios están conectados; el aislamiento entre organizaciones es total (RLS).
- Regla de oro: nada cuenta como hecho sin prueba real. Una integración solo está «verificada» contra la API real en staging, con ids del proveedor.

## 3. Arquitectura
```
 Cliente final                      Equipo del negocio
 (WhatsApp · chat web)              (navegador / PWA)
        │ webhook firmado                  │ sesión Supabase Auth (+MFA aal2 para administrar)
        ▼                                  ▼
 ┌──────────────────────┐          ┌──────────────────────┐
 │ apps/worker (Railway)│          │ apps/web (Vercel)    │
 │ Node + DBOS Transact │          │ Next.js App Router   │
 │ ingress → turno del  │          │ bandeja, aprobaciones│
 │ agente → envío       │          │ agenda, ajustes      │
 │ outbox · recordat.   │          │ requireUser() en     │
 │ integraciones · KMS  │          │ servidor             │
 └───────┬───────┬──────┘          └──────────┬───────────┘
         │       │ rol moodly_worker          │ cliente con la sesión
         │       │ (RLS + organization_id)    │ (RLS + guardas guard_*)
         │       ▼                            ▼
         │   ┌────────────────────────────────────────────┐
         │   │ Supabase Postgres (UE): RLS en todo,       │
         │   │ pgvector, esquema dbos, domain_events      │
         │   │ (outbox), approvals, inbound_events        │
         │   └────────────────────────────────────────────┘
         ▼
 Terceros: Vercel AI Gateway (modelos) · Meta WhatsApp Cloud API ·
 Nango (OAuth Google/Outlook) · Koibox · AWS KMS · Resend
```
- Paquetes: `agent-core` (runtime, políticas, aprobaciones), `skills` (lo que el agente sabe hacer), `channels`, `integrations`, `knowledge`, `db` (migraciones, pgTAP, clientes), `config` (modelos, marca, TTLs), `evals`, `ui`, `templates`, `domain`.
- Mensaje entrante: webhook firmado → `inbound_events` → la cuenta de canal da la organización (nunca el payload) → workflow DBOS → `converse` → respuesta autónoma o borrador en `approvals` → envío. Un mensaje nuevo a mitad de turno releva al anterior.
- Despliegue: CI verde en `main` → «Despliegue a staging»: migraciones → web (Vercel) y worker (Railway) con el commit exacto. Producción no existe todavía.
- Mapa de carpetas completo: `docs/ARCHITECTURE.md`.

## 4. Cómo se trabaja en una fase
- Un Lead por fase (planifica, reparte, revisa y mergea; solo edita `docs/`). Un worker por subfase, en sesión nueva; 2 en paralelo, 3 solo si no comparten archivos ni migración.
- Modelos de worker: Opus con esfuerzo alto si toca auth, RLS, migraciones, datos de clientes, permisos de agentes, pagos, integraciones o el worker; Opus medio para el resto de código; Sonnet alto para docs y tareas mecánicas.
- El merge es siempre de uno en uno (`docs/specs/ola0-00-como-mergear.md`): `main` exige rama al día, así que cada merge son unos 25 min de CI sobre la rama actualizada.
- Skills: el Lead mira `.claude/toolkit/SKILLS-INDEX.md` y escribe la línea «Skills» de cada spec (0–2).
